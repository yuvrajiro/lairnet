Development
===========

Run the tests from the standalone package root:

.. code-block:: bash

   python -m pytest

Build the documentation:

.. code-block:: bash

   sphinx-build -b html -W --keep-going docs docs/_build/html

``-W`` is not decoration. A malformed docstring renders as a mangled API page
and nobody reads a build log that always has warnings in it.

Regenerating what the docs show
-------------------------------

Neither the figures nor the notebook outputs are produced by the Sphinx build.
``nb_execution_mode`` is ``off``, so a page shows what the code did rather than
what it is expected to do -- but only because one of these ran first:

.. code-block:: bash

   python docs/make_gallery.py     # the six PNGs, and the summary the pages quote
   python docs/make_notebooks.py   # writes and executes docs/examples/*.ipynb

Run both with the same interpreter. ``make_notebooks.py`` pins the kernel to
``sys.executable`` and aborts if it does not get it, because the ambient
``python3`` kernelspec can be an entirely different environment: when it was, a
different scipy took L-BFGS down a different path and the notebooks published
0.8476 for the fit the gallery documents as 0.8369.

The notebook *sources* are generated by ``make_notebooks.py``, so editing a
committed ``.ipynb`` in Jupyter will be overwritten. Change the cell text in the
script.

Documentation gates
-------------------

Two things Sphinx will never complain about, both of which have already gone
wrong here:

.. code-block:: bash

   python docs/check_styles.py          # a class named in a page with no CSS rule
   python docs/check_numbers_agree.py   # pages quoting numbers the notebook did not produce

``check_styles.py`` catches a class that has no rule at all. It cannot catch a
rule that exists and loses on specificity -- the theme ships
``.docutils.container { max-width: unset }``, which silently discards any width
written as a bare ``.hero-lede``. That one needs a browser and computed styles.

Build and check release artifacts:

.. code-block:: bash

   python -m build
   twine check dist/*

Benchmarking rules:

- report repeated trials, not one-off timings;
- prevent overlapping benchmark runs;
- compare time to a common objective value when optimisers converge at different
  rates;
- do not document a speed claim until the benchmark records support it.
